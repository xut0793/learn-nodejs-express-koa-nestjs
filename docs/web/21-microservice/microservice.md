# 微服务 Microservice

微服务（Microservice）这个概念最早在2012年提出，作为适应移动互联网时代应用程序开发的一种方法。在马丁.福勒 (Martin Fowler) 的大力推广下，2014年可以认为是微服务1.0的元年，当年有几个标志性事件：

1. 一是 Martin Fowler 在其博客上发表了 “Microservices” 一文，正式提出微服务架构风格；
2. 二是 Netflix 微服务架构经过多年大规模生产验证，最终抽象落地形成一整套开源的微服务基础组件，统称 NetflixOSS，Netflix 的成功经验开始被业界认可并推崇；
3. 三是 Pivotal 将 NetflixOSS 开源微服务组件集成到其 Spring 体系，推出 Spring Cloud 微服务开发技术栈。

> Martin Fowler 是国际著名的OO专家，敏捷开发方法的创始人之一，现为 ThoughtWorks 公司的首席科学家。在面向对象分析设计、UML、模式、软件开发方法学、XP、重构等方面，都是世界顶级的专家，现为 Thought Works 公司的首席科学家。早在20世纪80年代，Fowler就是使用对象技术构建多层企业应用的倡导者，他著有几本经典书籍：《企业应用架构模式》、《UML精粹》和《重构》等。

到目前而言，微服务技术生态又发生了巨大变化，比如容器 docker，PaaS，Cloud Native，gRPC，ServiceMesh，Serverless 等新技术新理念对微服务的影响，使得微服务架构进货到 2.0 时代。

但是对于微服务业界并没有一个统一的、标准的定义，但是还是可以从马丁.福勒 (Martin Fowler) 对微服务的概述中了解它的含义：

> 1. 微服务架构是一种架构模式，它提倡将单一应用程序划分成一组小的服务，服务之间互相协调、互相配合，为用户提供最终价值。
> 1. 每个服务运行独立的自己的进程中，服务之间采用轻量级的通信机制互相沟通（可以是 RESTful API，或者 RPC） 。
> 1. 每个服务都围绕着具体业务进行构建，并且能够被独立地部署到生产环境、类生产环境等。
> 1. 另外，应尽量避免统一的、集中式的服务管理机制，对具体的一个服务而言，应根据业务上下文，选择合适的语言、工具对其进行编写和构建，可以使用不同的数据存储，也可以有一个非常轻量级的中心服务来协调和管理这些服务。

总结上述内容，可以简单理解微服务为：将单体应用（Monolithic application）应用拆分成各种小的、互相连接的微服务，一个微服务完成一个比较单一的功能，相互之间保持独立和解耦合。

在这个将单体应用拆成数个微服务的过程中，需要考虑以下问题：

1. 服务如何拆分
2. 服务拆分后，对于客户端请求如何做统一的访问控制 => 网关 Gateway
3. 每个服务之间如何通信 => RESTful 或者 RPC
4. 如何发现新的服务 => 服务注册和发现
5. 某个服务挂了，如何解决 => 服务容错机制（负载均衡、限流、熔断、降级、缓存等）
6. 这么多微小服务如何部署和运维 => devops

以上所有问题的解决方案，统称为“微服务架构”（Microservices Architecture）。

## 服务拆分

横向拆分：按照不同的业务域进行拆分，例如订单、物流、积分等。形成独立的业务领域微服务集群。

纵向拆分：把一个业务功能里的不同模块或者组件进行拆分。例如把公共组件拆分成独立的原子服务，下沉到底层，形成相对独立的原子服务层。

这样一纵一横，就可以实现业务的服务化拆分。要做好微服务的分层：梳理和抽取核心应用、公共应用。作为独立的服务下沉到核心和公共能力层，逐渐形成稳定的服务中心，使应用能更快速的响应多变的市场需求。

总之，微服务的设计一定要 渐进式 的，总的原则是 服务内部高内聚，服务之间低耦合。

拆分后的微服务特点：

- 单个微服务业务功能单一，独立，易于维护
- 每个微服务都有自己独立的基础组件，例如数据库、缓存等且运行在独立的进程中
- 单个微服务能够集群化部署，并且有负责 均衡的能力

## 服务网关

> 可以把网关理解为小区的门卫，对进入小区的人员进行身份检查等操作，从小区大门外部也无法探知小区楼栋情况。

在微服务系统中，API 接口资源通常是有服务网关（也称API网关）统一暴露，内部服务不直接对外提供API资源的暴露。

网关层通常以集群的形式存在，并在服务网关层前通常会加上Nginx 用来负载均衡

网关意义：

- 统一路由：网关将所有服务的API接口资源统一聚合，对外统一暴露，让微服务对前台透明
- 安全认证：网关可以做一些用户身份认证，权限认证，防止非法请求操作API 接口，对内部服务起到保护作用
- 日志监控：网关可以实现监控功能，实时日志输出、对请求进行记录
- 限流熔断：网关可以用来做流量监控，在高流量的情况下，对服务进行降级
- 方便测试：API 接口从内部服务分离出来，方便做测试

当然，网关实现这些功能的同时，需要做高可用，否则网关很可能成功架构的瓶颈，最常用的网关组件 Zuul、Kong、Nginx

## 服务通信

每个微服务都是独立的，比如 java 程序中，每个微服务都是独立的进程跑在虚拟机上，所以服务间的通信就是 IPC （inter process communication），而 IPC 通信有很多成熟的方案。比如：

- 同步调用
  - REST
  - RPC（Thrift, Dubbo, gRPC）
- 异步消息队列通信：Kafka、RabbitMQ

## 服务发现和注册

在微服务架构中，一般每一个服务都是集群部署，来做负载均衡。一个服务随时可能下线，也可能应对临时访问压力增加新的服务节点。这么多微服务之间如何相互感知？服务如何管理？

这就是服务发现的问题了。一般有两类做法，也各有优缺点。基本都是通过zookeeper等类似技术做服务注册信息的分布式管理。当服务上线时，服务提供者将自己的服务信息注册到ZK（或类似框架），并通过心跳维持长链接，实时更新链接信息。服务调用者通过ZK寻址，根据可定制算法， 找到一个服务，还可以将服务信息缓存在本地以提高性能。当服务下线时，ZK会发通知给服务客户端。

常见的服务注册组件有 zookeeper、Eureka

## 服务配置

单体应用的时候所有的配置都可以集成在服务系统之中，微服务的时候如果每个服务都持有一份配置可能会有相同配置冗余的情况，并且更多的配置和更多微服务必然会带来管理上的混乱，所以服务的配置信息需要一个集中管理的地方。

配置中心的实现基本上就是推送-订阅模式的运用。配置的应用方是订阅者，配置管理服务则是推送方。其中，客户端包括管理人员 publish 数据到配置管理服务，可以理解为添加/更新数据；配置管理服务 notify 数据到订阅者，可以理解为推送。配置管理服务往往会封装一个客户端库，应用方则是基于该库与配置管理服务进行交互。在实际实现时，客户端库可能是主动拉取(pull)数据，但对于应用方而言，一般是一种事件通知方式。

选型一个合格的配置中心，至少需要满足如下4个核心需求：

- 非开发环境下应用配置的保密性，避免将关键配置写入源代码；
- 不同部署环境下应用配置的隔离性，比如非生产环境的配置不能用于生产环境；
- 同一部署环境下的服务器应用配置的一致性，即所有服务器使用同一份配置；
- 分布式环境下应用配置的可管理性，即提供远程管理配置的能力。

常用的配置中心组件有 Diamond（阿里）、Apollo（携程）、Spring Cloud Config

## 服务容错（服务治理）

单体应用（Monolithic application）开发一个很大的风险是，把所有鸡蛋放在一个篮子里，一荣俱荣，一损俱损。而分布式最大的特性就是网络是不可靠的，通过微服务拆分能降低这个风险，不过如果没有特别的保障，结局也是噩梦。所以当我们的系统是由一系列的服务调用链组成的时候，我们必须确保任一环节出问题都不至于影响整体链路，也就是整体系统要有一定的容错措施，相应的手段有很多：

- 负载均衡
- 限流
- 熔断机制
- 降级
- 缓存
- 重试

这些方法基本都很明确通用，常用的组件有 Sentinel、Hystrix、Resilience4j

## 服务部署

服务的部署从物理机到虚拟机，从虚拟机到容器；从物理集群到 OpenStack，从 OpenStack 到 Kubernetes 不断变化。

在实现上通常会有整套 Devops 系统来完成。

## 服务监控

监控预警对于微服务很重要，一个可靠的监控预警体系对微服务运行至关重要。

一般监控分为以下层次：

- 端用户侧监控：性能、访问量等
- 业务监控：系统核心指标
- 应用层监控：qbs、cache 等
- 系统层监控：cpu、memory 等
- 基础设置监控：网络流量、转接数、丢包等

每层监控系统基本功能点：

- 日志监控：ELK
- Metrics 监控
- 健康检查
- 调用链跟踪：cat、zipkin、pinpoint、skywalking
- 告警系统

## 微服务框架

> 架构是一种设计思想和方法，通常约定了它的基本结构和组成，以及实现的规范。架构之后，需要进一步梳理架构中各个组成部分可实现的技术体系，最后使用技术进行实现。

目前常用微服务框架 Spring Cloud 是一个基于 Spring Boot 实现的微服务架构解决方案，它提供了一套微服务开发所需的规范和标准。定义了一系列开发微服务应用的模式和组件，比如服务注册和发现、配置中心、负载均衡、网关等，但并不提供具体实现。所以基于 Spring Cloud 微服务架构的实现，形成了两种微服务生态：

- Spring Cloud Netflix：是微服务最早期的一个实现，后面 Spring Cloud 最初也是基于它定义了一系列组件规范。但从 2018年12月12日起，Netflix 公司宣布停止对开源组件的维护，转而推荐社区自行维护。所以 Spring Cloud 官方也在推出替代组件。
- Spring Cloud Alibaba：阿里提供的微服务解决方案，在实际应用中只需要再添加少量配置和组件即可使用。

## SOA

过去传统的一个大型而又全面的单体应用，随着互联网的发展已经很难满足市场对技术的需求，于是我们从单体架构发展到分布式架构，又从分布式架构发展到 SOA 架构，服务不断的被拆分和分解，粒度也越来越小，直到微服务架构的诞生。

面向服务的架构 SOA (Service-Oriented Architecture) 将大型应用按功能拆分为独立的服务，这些服务使用基于xml的语言描述可调用接口，服务之间通过事件总线进行通信。

SOA 架构紧密相关的技术主要有 UDDI、WSDL、SOAP 和 REST 等，而这些技术都是以 XML 为基础而发展起来的。

- UDDI（Universal DescriptionDiscovery and Integration，统一描述、发现和集成）提供了一种服务发布、查找和定位的方法，是服务的信息注册规范，以便被需要该服务的用户发现和使用它。包括描述业务组织和服务的 XML Schema、API、服务注册中心。
- WSDL（Web ServiceDescription Language，Web 服务描述语言）是对服务进行描述的语言，它有一套基于 XML 的语法定义。WSDL 描述的重点是服务，它包含服务实现定义（服务和端口）和服务接口定义（消息、类型、绑定）。
- SOAP（Simple ObjectAccess Protocol，简单对象访问协议）定义了服务请求者和服务提供者之间的消息传输规范。SOAP 用 XML 来格式化消息，用 HTTP 来承载消息。通过 SOAP，应用程序可以在网络中进行数据交换。
- REST（RepresentationalState Transfer，表述性状态转移）是一种只使用 HTTP 和 XML 进行基于 Web 通信的技术，使它与SOAP很好的协作。

SOA 架构的实现方式之一，就是采用企业服务总线的方式，称为 ESB（Enterprise Service Bus），是由中间件技术实现并支持 SOA 架构的可落地方案。

![SOA ESB](..../../public//soa_esb.png)

微服务架构可以看作是SOA的一种演进，它强调服务的轻量化（小且专注一个功能、轻量级通信）、独立性和敏捷性。两者的细微区别：

> 可以将 SOA 是大企业中的事业部 BU，微服务是大企业中更小更独立的业务子公司。

1. 服务粒度：

- SOA：面向服务架构中的服务通常具有较大的粒度，它们可能包含多个功能模块。SOA服务通常关注业务功能的整合和重用。
- 微服务：微服务架构中的服务粒度更小，每个服务通常只负责一个特定的功能。微服务关注单一职责原则，使得服务更加轻量化和独立。

2. 服务独立性：

- SOA：SOA服务可能共享相同的数据存储、基础设施和资源。这可能导致服务之间的耦合度较高。
- 微服务：微服务架构强调服务的独立性，每个服务都有自己的数据存储、基础设施和资源。这有助于降低服务之间的耦合度，提高系统的可维护性和可扩展性。

3. 通信协议：

- SOA：SOA通常使用复杂的通信协议，如SOAP（Simple Object Access Protocol）和WS-\*（Web Services）规范。
- 微服务：微服务架构倾向于使用轻量级的通信协议，如RESTful API和gRPC。

4. 部署和运维：

- SOA：SOA服务通常部署在集中式的应用服务器上，这可能导致部署和运维的复杂性较高。
- 微服务：微服务架构支持独立部署和运维，每个服务可以单独进行扩展、更新和维护。这有助于提高系统的敏捷性和可靠性。

5. 技术栈：

- SOA：SOA服务通常使用统一的技术栈和平台，这可能限制了技术的多样性和灵活性。
- 微服务：微服务架构允许每个服务使用不同的技术栈和平台，这有助于提高技术的多样性和灵活性。
