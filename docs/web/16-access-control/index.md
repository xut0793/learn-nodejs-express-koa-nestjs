## What

什么是用户访问控制？简单说就是在 BS（Browser / Server 浏览器/服务器） 架构下，对访问用户进行认证（Authentication: 你是谁）、授权（Authorization 你能干什么）和鉴权（Audit 确定是你在做）的过程。

- Authentication（认证） 是验证您的身份凭据 identified（例如用户名/用户ID和密码），通过这个凭据，系统才能知道你就是你，也就是说系统存在你这个用户。
- Authorization（授权） 发生在 Authentication（认证）之后。为用户分配系统资源的访问的权限，比如有些特定资源只能具有特定权限的人才能操作。授权的结果是下发一个包含权限信息的凭证 credential，再次访问时需要携带该凭证，进行鉴权。
- Audit（鉴权）发生在用户访问系统资源时，通过携带的授权凭证，系统确认当前用户是否有该资源的访问权限。

> 访问控制的“黄金法则”
>
> 这和黄金有什么关系？这要从它们三个概念的英文单词说起，认证就是 Authentication，而授权对应的是 Authorization，鉴权对应的英文是 Audit。它们三个单词的前两个字母都是“Au”，而在元素周期表中，金元素对应的字母表示正是“Au”。这便是“黄金法则”的由来。当然，除了叫做“黄金法则”外，有时也会只取这三个单词中的首字母，称为 AAA 法则，或者叫 3A 法则。如果 3A 法则你也没听过，那么，A & A 你一定经常听到过吧？这时，就是省去了鉴权，A&A 指的就是认证和授权（即 Authentication & Authorization，时常也会被缩写为 AN 和 AZ，或者 AuthN 和 AuthZ）。
>

## Why

为什么需要控制用户访问？BS 架构下的连接是通过 HTTP(s) 网络进行请求和响应，但 HTTP(s) 连接的一个主要特点是**无状态**。每一次访问连接都需要让系统知道是谁在操作，但不可能每一次连接请求都让用户重复登录来进行验证，所以需要一种机制来维持登录态。

## How

用户访问控制，简化的流程：

```
Browser 浏览器    HTTP                Server 服务器
               个人信息
     +--------------------------->
注册                                  生成唯一标识符 identifier 标识用户
     <--------------------------+
               identifier              ^
                                       | identifier
               identifier              +
      +---------------------------->  认证 Authentication (AuthN) 你是谁
登录
      <----------------------------+  授权 Authorization (AuthZ) 你能做什么（授予特定用户操作特定的资源的权限）
               凭证 credential

               凭证 credential
     +---------------------------->
访问                                  鉴权 Audit 是不是你能做的（核对用户是否有授予操作该资源的权限）
     <----------------------------+
              响应资源 resource

```

- 注册：通过注册表单或其它方式，将用户进行唯一标识(identified)，然后将用户标识进行存储，比如数据库中存储的 userId、账号、手机号、邮箱等能识别用户的唯一性字符。
- 登录：用户需要向访问的系统证明自己是谁，所以登录时需要提供注册时的唯一标识符，比如账号(userId)、手机号、邮箱之类的。
- 认证：服务端逻辑，将用户登录时提供的信息进行确认系统是否存在当前用户。
- 授权：认证通过后，服务端通过某种授权方式，生成一个特殊的包含权限信息的凭证，返回给客户端进行保存。
- 访问：客户端再次访问系统资源时，需要携带凭证给服务端进行鉴权。
- 鉴权：验证当前凭证是否有效，并且验证是否有请求资源的操作权限。

## 注册

注册的主要目的是用来收集特定的用户信息，方便服务端来生成用户的唯一标识符。

常用来作为唯一性标识的个人信息包括：

- 账号密码，通常在注册页面填写一个账号，提交时会校验账号其唯一性，或者提交密码等资料后由系统分配一个唯一性账号。比如早期的 QQ 号。
- 邮箱具有唯一性，注册时通过向邮箱发送验证码或验证链接，校验邮箱是否真实有效。
- 手机号码具有唯一性，注册时通过向手机发达验证码，校验手机号是否真实有效。
- 第三方授权，利用已注册过的第三方平台返回的唯一用户标识符标记用户。
- 新型方式：录入指纹信息、脸部信息、手势密码等。

对 B 端系统，一般都会有一个唯一的工号来标识员工，这些信息在内部数据库可查，所以使用 toB 的系统时一般是不会有注册页面的，使用工号或分配的公司邮箱直接进行登录。

## 登录

对应注册的方式，登录方式常见的有：

- 账号 + 密码
- 邮箱 + 密码
- 手机号 + 密码
- 跳转第三方系统授权登录，常见于 toC 系统
- 单点登录 SSO，常见于 toB 的企业内部多系统登录，但如 PC 端网页的淘宝、天猫也是单点登录的示例。
- 新型方式：指纹、手势、人脸识别等。

随着互联网发展，为了应对爬虫或机器人的自动登录，校验是机器还是真人操作，一般会在首次登录或频繁登录出错后，出现安全码校验。安全码的常见形式有：

- 邮箱或手机，发送验证码或验证链接
- 额外输入随机字符、数字等
- 滑动条或滑动拼图

如何进行登录？我们能见到的大部分场景都是应用有自己独立的登录页面，比如在 B 端系统中，更常见的页面形式是填写登录表单。

## 认证 Authentication (AuthN)

服务端接收用户在浏览器登录表单中输入的用户信息后，通过认证后，当再次访问其它资源时，如何认证这些用户还是之前登录过的用户呢？

换个说法：如何解决 HTTP(s) 的无状态性，即如何维持 HTTP 的登录态？

- 最初的方法 Cookie / Session
- 通用的 HTTP Authentication 认证框架。常见的验证方式有 Basic / Digest / Bearer 等。[HTTP Authentication](https://developer.mozilla.org/zh-CN/docs/Web/HTTP/Authentication)
- OIDC: OpenID Connect 联合身份认证
- OAuth 协议，包含了身份认证和授权两部分内容

## 授权 Authorization (AuthZ)

这里的授权环节，包含两部分内容：

- 如何设置资源的访问权限
- 如何响应授权凭证

### 授权模型

和其它IT技术演进一样，常见的各类授权模型也是按业务场景慢慢完善的，按演进时间线，常见的有：

- 访问控制列表 (Access Control List, ACL)
- 强制访问控制 (Mandatory Access Control, MAC)
- 自主访问控制 (Discretionary Access Control, DAC)
- 基于角色的访问控制 (Role-Based Access Control, RBAC)
- 基于属性的访问控制 (Attribute-Based Access Control, ABAC)

### 响应授权凭证

根据采用的授权模型不同，需要响应的授权凭证形式也不同。

- 比如对于访问控制列表或强制访问控制等，访问权限信息完全在服务端定义，再次访问鉴权时只需要用户凭证即可，此时用户凭证可以作为授权凭证，通过 set-cookie 下发到客户端。
- 比如基于角色的访问控制，如果将角色信息进行响应？常见的是将用户信息和角色信息进行 JWT 编码后生成 token 作为授权凭证响应。

## 访问：携带凭证

根据采用的授权模型不同，浏览器接收授权凭证的方式也不同，当再次访问请求时，如何携带授权凭证的方式也不同。

大体分为两类：

- 浏览器自主处理：比如服务器响应时设置 set-cookie 头字段，那么浏览器访问资源时，请求会自动附加 cookie 头字段。这一切都是浏览器自动完成。
- 业务逻辑自行实现：比如遵循 HTTP Authenticate 认证框架，通过 Authorization 请求头字段。

## 鉴权 Audit

遵循选定的授权模型，进行对应方式的验证。

## 延伸知识点：区分 Authentication(AuthN) 和 Authorization(AuthZ)

[区分 Authentication(AuthN) 和 Authorization(AuthZ)](https://xsun4231.github.io/2019/07/09/AuthN-vs-AuthZ/)

### 别直接用Auth来命名

之前对于Auth这个关键字的理解，一直都处于大概知道什么意思的模糊状态。其实使用Auth作为关键字来命名方法和变量，并不是很合适，因为Authentication 和 Authorization 的缩写都可以是Auth。

- Authentication 翻译是认证，用来确认你是谁，比如输入用户名和密码，系统判断这个用户名存在，且密码匹配，就是认证，通常缩写为 AuthN。
- Authorization 翻译是授权，允许你能做什么，例如确认你是合法用户后，给你在系统内可以访问的资源，就是授权，通常缩写为 AuthZ。

### 区分 401 和 403

HTTP的返回值401和403是一对很容易弄混的数字。

- 401 Unauthorized，发生用户认证错误时的响应。虽然写着 Unauthorized 的文本信息，返回的却是 Authentication 认证的错误。
- 403 Forbidden，发生在鉴权时不在允许范围内拒绝访问的响应。承担着返回 Unauthorized 错误的职责。

可以按前后顺序来记忆，在大小上，401在403前面，在流程中，认证在鉴权前面，单词顺序上 AuthN 的 N 在 AuthZ 的 Z 前端。所以`认证 => AuthN => 401` 和`授权 => AuthZ => 403`。
